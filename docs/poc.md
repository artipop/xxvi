# Что входит в PoC

Границы первой версии. Формализация системы — в [system.md](system.md); здесь
только то, что из неё реализуется сейчас, и то, что сознательно отложено.

## Задача PoC

Есть источник с задачами и пара заранее готовых флоу. Флоу можно править.
Карточки спокойно проходят по флоу от входящих до конца.

## Решения по объёму

| Вопрос | Решение | Почему |
|---|---|---|
| Источник | локальный демо-источник: файл `items.jsonl` + добавление руками из UI | оффлайн, без токенов и сети; показывает и группировку по источникам, и правила. Протокол источников из XCIII переносится целиком, реальные коннекторы добавляются позже |
| Вход во флоу | только вручную: «В работу» + выбор флоу | «почему эта карточка поехала» всегда имеет ответ |
| Триггеры | `success`, `failure`, `blocked`, `card.changed` + ручной перевод | никакого поллинга внешнего мира; PoC самодостаточен |
| Агенты | только настоящие ACP-адаптеры (claude, codex, произвольная ACP-команда) | агенты по ACP — это половина смысла приложения, подделывать её нечем |

## Что есть

- **Входящие**, сгруппированные по источникам. Карточка из элемента источника
  или заведённая руками.
- **Демо-источник**: читает `items.jsonl` из своей папки и принимает элементы,
  добавленные из UI. Правила: `card` / `comment` / `drop`, регэкспы по
  заголовку, тексту и меткам.
- **Флоу**: граф стадий и переходов, два готовых («Разработка», «Проверка
  человеком»), редактор графа.
- **Стадии** с действиями `none` и `agent`, промптом, составом агентов и
  лимитом одновременных сессий; очередь на занятую стадию.
- **Переходы** с условиями по свойству карточки и по словам агента.
- **Агенты по ACP**: реестр, проверка доступности адаптера, запуск сессии,
  поток вывода в комментарии карточки.
- **HITL**: вопросы агента (`request_permission` и elicitation), отметка на
  карточке, панель «Требуют внимания», ответ из панели и с карточки.
- **Журнал**: комментарии карточки и журнал переходов — на любой вопрос «почему
  карточка здесь» есть ответ в интерфейсе.

## Чего нет и почему

| Не делаем | Почему |
|---|---|
| Канбан-доска | её отсутствие — и есть смысл этого приложения |
| git-worktree, ветки, деплой, браузерные тесты | тянут за собой git, Dokku и Playwright; на движок флоу не влияют |
| `git.*` и `github.*` триггеры | требуют поллинга и токенов. Место в модели предусмотрено: у триггера есть `source`, добавление не меняет ни движок, ни редактор |
| Терминал с агентом | отдельная большая подсистема (pty, xterm); в PoC разговор с агентом идёт через вопросы |
| Реальные коннекторы (почта, трекеры, OAuth) | демо-источник показывает ту же механику без учёток |
| Прокси, MCP-серверы агента, секреты | настройки одного агента, не механика флоу |
| Синхронизация между машинами | одна SQLite на машине |

## Порядок работ

1. Формализация (`docs/`).
2. Модель и SQL-хранилище.
3. Движок флоу поверх хранилища, с тестами.
4. Источники: реестр, правила, демо-плагин.
5. Агенты по ACP: реестр, сессии, вопросы.
6. Фронт на Solid: входящие, карточка, внимание, редактор флоу.
7. Готовые флоу и демо-данные.
