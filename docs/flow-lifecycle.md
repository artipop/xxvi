# Работа с флоу

Эксперимент в `experiment/flow-lifecycle`.

У человека есть место, где он смотрит, у карточки — стадия, где сейчас делается
работа. Это могут быть разные места. Просмотр старого терминала не запускает
агента и не меняет маршрут.

## Два выбора на ноде

| Настройка | Варианты | По умолчанию |
|---|---|---|
| Запуск работы | Автоматически при входе / по кнопке «Запустить шаг» | Автоматически |
| При входе на ноду | Показать её на ленте / оставить текущий экран | Показать |

Ручной запуск относится к действию ноды: агенту, публикации или вердикту.
На такой ноде карточка уже стоит, экраны доступны, но действие ещё не запущено.
Она появляется в «Ждут ответа» как ожидающая запуска. Ожидание сохраняется
после перезапуска приложения. Кнопка относится к конкретному посещению ноды:
двойной или запоздавший клик не запускает следующий шаг.

Нода ожидания ничего сама не выполняет: она ждёт свойства или внешнего события.
Финал закрывает карточку сразу. У этих нод нет выбора запуска.

Переход фокуса действует только на открытую ленту. Если человек сам ушёл
посмотреть другой экран, приложение его не перетягивает. Кнопка перехода к
текущему шагу доступна и при отключённом автоматическом фокусе. Явные команды
«Запустить шаг» и «Вернуться к этому шагу» показывают место начатой работы.

## Завершение шага

`finish_step` принимает исход, итог и обязательные выходы. Движок записывает
выходы, выбирает ребро и входит в следующую ноду. Её настройка определяет,
запустится ли следующее действие сразу. Обычное окончание ответа CLI ничего
не завершает; закрытие процесса тоже не считается успешным результатом.

Завершённый CLI остаётся на экране. Он больше не занимает слот стадии, не
принимает ввод и не может повторно отчитаться в карточку. Инструкции MCP
говорят агенту прекратить работу после отчёта: следующий шаг может сразу
работать в той же папке.

## Вернуться и дописать

На законченном терминале с сохранённым id разговора есть **«Вернуться к этому
шагу»**. Это явная смена текущей работы:

1. Текущий агент получает отмену. Новый запуск ждёт завершения старого.
2. Создаётся новое посещение выбранной стадии; прежние результаты остаются
   в своих сегментах ленты.
3. CLI открывает выбранный разговор через `--resume <id>` без реплики и без
   повторной отправки задачи. Человек смотрит историю и пишет сам.
4. Новый `finish_step` снова ведёт по рёбрам этой стадии.

Работает и у завершённой карточки: возврат снова делает её рабочей. Если
исполнитель карточки изменился, выбранный разговор открывается своим прежним
агентом; дальнейшие стадии используют текущего исполнителя карточки.

Пока выполняется публикация или на стадии нет свободного слота, возврат
отказывается запускаться. Удалённая нода, другой вид агента или утраченный id
разговора тоже дают явный отказ. Разговор не выбирается по последнему файлу в
общей папке.

## Что сохранено, а что перезапускается

При переходе на следующую ноду процесс предыдущего CLI остаётся жив. При
возврате в этот разговор старый процесс закрывается, а новый получает его
точный id и права нового шага. Это эксперимент с сохранением разговора,
а не переназначение живого процесса между посещениями. После закрытия
приложения завершённые терминалы доступны как снимки; незаконченные разговоры
с известным id ждут «Открыть разговор» или «Продолжить».

Закрытие незаконченного CLI после старта при известном id ставит шаг на паузу.
Карточка не удаляется из-за закрытия терминала. Ошибка запуска остаётся ошибкой
и может вести по ребру `failure`.

## Почему переход воспроизводим

Каждое посещение — отдельный `flow_event`. Запуск хранит его id в
`agent_session.visit_id`, поэтому принадлежность к сегменту не зависит от
совпадения временных меток. Отчёт относится к посещению, выдавшему задание:
после ручного возврата поздний отчёт прежнего запуска не меняет ни свойства,
ни положение карточки. События отмены освобождают очередь стадии, но не
выбирают ребро.

Проверки: ручной запуск после пересоздания движка, повторный клик, старый клик
после нового посещения, цикл с возвратом к конкретному разговору, поздние
отчёты, история при одинаковых временных метках, настоящий PTY и MCP без
обращения к модели. Живые Claude/Codex и визуальное поведение Ghostty требуют
отдельного прогона в приложении.
