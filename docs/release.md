# Выпуск

Выпуск — один push. Всё остальное делает `.github/workflows/release.yml`.

```
wails3 task version:set VERSION=0.2.0
git commit -am "версия 0.2.0"
git tag -a v0.2.0        # аннотация тега = что человек прочтёт в «Обновлении»
git push && git push --tags
```

Тег, чья версия не совпадает с деревом, роняет сборку до того, как что-то
опубликуется. Это дешевле, чем узнать об этом от того, кому приложение вечно
предлагает обновиться до версии, которая у него уже стоит.

## Что где написано

| Где | Что |
|---|---|
| `version.go` | версия, которой называет себя сборка и которую сравнивает апдейтер |
| `internal/buildversion` | список всех файлов, где версия написана ещё раз |
| `version_test.go` | падает, когда они разошлись |
| `updates.go` | адрес ленты релизов и канал — их же читает workflow |
| `build/updater.key.pub` | ключ, которым сборка проверяет подпись манифеста |

`wails3 task version:set` пишет число во все файлы разом. Не
`common:update:build-assets`: он переписывает сборочные файлы из шаблонов CLI, и
всё, что в них написано руками, уезжает вместе с ними.

## Ключ

Релизы подписываются Ed25519-ключом. Публичная половина —
`build/updater.key.pub` — лежит в репозитории и вкомпилирована в каждый бинарь
(`//go:embed` в `updates.go`), поэтому лента не может решать, каким ключом её
проверять. Приватная половина живёт **только** в секретах CI и в менеджере
паролей; в репозиторий она не попадает (`.gitignore`).

Новую пару делает `wails3 updater genkey -out build/updater.key`. Менять её у
уже установленных копий нельзя: они проверяют подпись тем ключом, с которым
собраны, и манифест, подписанный новым, для них — чужой.

## Секреты

| Секрет | Зачем |
|---|---|
| `UPDATER_PRIVATE_KEY` | приватная половина ключа: ею подписывается манифест |
| `RELEASES_S3_ENDPOINT` | адрес S3-совместимого хранилища |
| `RELEASES_S3_BUCKET` | бакет, из которого раздаются файлы |
| `RELEASES_S3_ACCESS_KEY_ID`, `RELEASES_S3_SECRET_ACCESS_KEY` | доступ к нему |

## Куда что кладётся

Бакет раздаётся под `https://updates.deffun.org/`, и это **единственный адрес,
который установленная копия уже не переучить**: она спрашивает там и больше
нигде. Поэтому это домен наш, а не страница релизов на чьей-то платформе — где
лежат файлы, можно пересмотреть в любой выпуск, а эту строку нельзя.

```
updates.deffun.org/xxvi.json          ← манифест последнего выпуска
updates.deffun.org/v0.2.0/…           ← файлы этого выпуска, навсегда
```

Файлы уезжают **раньше** манифеста, и порядок здесь — суть: манифест и есть
объявление, что выпуск существует. Опубликуй его первым — и каждая копия,
которая в этот момент проверится, скачает 404 и покажет провалившееся
обновление у выпуска, с которым всё в порядке.

`dist/update/` — то, что ставит апдейтер; `dist/install/` — то, что человек
скачивает в первый раз. Манифест делается только по первой папке: инсталлятор,
подсунутый как приложение, заменил бы XXVI копией собственного инсталлятора.

## Что чем ставится

| Платформа | Обновляется | Ставится в первый раз |
|---|---|---|
| macOS | `.zip` с `.app` (ditto, не zip: bundle — это симлинки и xattr) | `.dmg` |
| Windows | `.exe` | NSIS-инсталлятор, `INSTALL_SCOPE=user` |
| Linux | `.tar.gz` | `.AppImage`, `.deb` |

Windows ставится в папку пользователя, а не в Program Files, по одной причине:
приложение в Program Files не может заменить собственный `.exe` без прав
администратора, то есть machine-scope установка — это установка, которая никогда
не обновится.

Linux `.deb` кладётся в `/usr` и по той же причине апдейтеру не предлагается
никогда: обновляемая форма — распакованный `.tar.gz` в папке, которой человек
владеет.

## Чего нет

**Подписи Apple и Windows.** Задачи в Taskfile есть, сертификатов нет, поэтому
macOS будет спрашивать про запуск подменённого бандла ровно так же, как
спрашивает при первой установке.

**Каналов.** Один адрес — один канал (`stable`). Поле в манифесте есть и
проверяется: манифест, попавший на этот адрес по ошибке, будет отвергнут, а не
установлен.

**Дельта-обновлений.** Скачивается весь бандл.
